# 場景同步等待與操作延遲修正（#438）

2026-11-26開始，2026-11-27完成本機驗證。使用者指定先處理大廳／競技場的移動、攻擊與Boss；基準為已合併3.37.0，`df5a8227e31e6c78e24191a3696106ff07100877`。候選3.37.1，發布／CI狀態以關聯PR的固定head紀錄為準，本輪未部署。

## 已重現及修正

1. `lobby.ts`原本在presenceJob存在時直接丟棄SSE state。移動POST或背景安全查詢等待越久，其他玩家、攻擊命中與Boss意圖越久無法更新。現在兩個傳輸來源都可交給既有快照解析／身分與serverNow防倒退檢查，不為慢HTTP停收推送。
2. 背景GET和移動共用presenceJob，GET最長可等待10秒，後來的移動也只能排隊。現在移動／瞬移可取消可替換的背景GET，立刻接續操作；仍只允許一個移動POST在途、後續目的地只保留最新一筆，不取消已送出的修改、不自動重送攻擊。
3. 慢HTTP失敗原本會直接把connected設為false，連同新目的地清掉。現在僅當stream仍開啟、請求期間確有更新快照且最近一筆在1500ms內時保留連線；沒有新有效快照、過期／格式錯誤資料或真正斷線仍走原重連與退避。

接收序號、單調時間及背景GET controller均隨reset清空；登出、卸載與隱藏仍取消請求／stream，不接受舊帳號資料。沒有增加推送頻率、網路重試、動畫或媒體預算；伺服器權威、判定、持有權與傷害不變。

## 實測結果

兩個獨立loopback服務、各自全新合成資料庫，分別載入3.37.0保存的正式bundle及本輪正式bundle；使用相同伺服器原始碼（本輪未改伺服器）。Edge桌機1920×1080／手機橫向844×390，以Playwright延遲完整HTTP回應1600ms，同時保留真實SSE及DOM演出。測試直接呼叫實際Pinia操作，並非量測硬體鍵盤輸入延遲。

競技場實際建立房間、準備、開始PK並等待5秒開場完成，使用同一人類與一隻被動機器人，沒有在房間選單冒稱驗過場內操作。競技場時序比大廳快是取樣當下SSE排程不同，不能保證每次都29ms。大廳第一輪的firstVisual採樣可能包含上一次尚未完成的走路，僅將有效的新moveId當主要比較；競技場補測則在新moveId後才計視覺更新。

另以兩隻攻擊機器人及一隻巨人Boss驗證慢移動POST期間的場景更新：回應延遲2600ms、觀察前2200ms，舊版收到0次更新，修正版在442／966／1549／2030ms收到4次更新並看見2筆攻擊。保留腳本／layout時間作煙霧檢查；不把舊版停收資料時較少的CPU工作誤稱為效能優勢。這不是百人容量或實體GPU FPS基準。

網路離線→恢復、模擬document.hidden→恢復於1920×1080、844×390及390×844通過，沒有pageerror。未驗實體裝置、ISP／Wi-Fi／跨區WAN延遲、代理緩衝與丟包；無法從本輪結果宣稱外網Ping降低。完整案例與數值保存於ignored `work/scene-latency-438`，不包含可登入憑證於公開文件。

## 回歸及檢查

- 修正前新增行為回歸有3項失敗：慢移動丟SSE、背景GET擋移動、舊HTTP失敗誤斷線；修正後通過。追加瞬移、串行／合併目的地、舊／錯誤／過期快照、登出舊stream拒收，共8項。
- `test:affected`因共用／未知路徑保守回退完整302檔：2559通過、0失敗、1缺FFmpeg略過，517.2秒；沒有以列計畫代替執行。最終前端全套420項通過，0失敗。
- 型別與正式build、UI（明確指定上述base）、模組邊界、來源／正式build素材預算、patch release及固定Prettier格式檢查通過。沒有新增素材或UI外觀，不提升baseline。

這一輪解決程式內部等待造成的場景停頓，不代表所有繪圖瓶頸或網路品質問題已解決。後續若仍有裝置掉幀，須另以固定多人場景量測渲染／long task／圖片解碼，不能沿用本輪網路數字證明GPU改善。
