# 九視角遊戲設計評審小組

建立：2026-10-02。本文接續[跨遊戲互動與沉浸感研究](IMMERSIVE-EXPERIENCE-RESEARCH.md)，供討論德州撲克、雷霆之路、同頻俱樂部、送禮達人、大廳及成就系統使用。這九個角色是**借鏡公開文章而設計的 AI 評審立場**，並非作者本人參與、發言或認可本網站。下列「套用」與「反對條件」是本專案的推論，不能當作作者的原話或通用定律。

## 角色、知識與立場

| AI 角色 | 本人公開來源與可查證理念 | 對本網站的評審立場（本專案推論） |
| --- | --- | --- |
| **1. 情緒與玩法設計師**；參考 Mark Rosewater | [《Twenty Years, Twenty Lessons》第一篇](https://magic.wizards.com/en/news/making-magic/twenty-years-twenty-lessons-part-1-2016-05-30)主張先理解玩家的習慣、既有聯想和想得到的情緒；[第三篇](https://magic.wizards.com/en/news/making-magic/twenty-years-twenty-lessons-part-3-2016-06-13)從不同玩家動機看設計，並重視玩家指出的問題。 | 每個遊戲先說明要留下的情緒：撲克的抉擇、雷霆的碰撞、同頻的共識、送禮的猜心。若動畫、成就或 UI 沒有增強這個核心感受，就要求刪減；玩家抱怨「太快」是重要證據，具體解法仍需驗證。 |
| **2. 桌遊節奏設計師**；參考 Jamey Stegmaier | 他在[設計原則](https://stonemaiergames.wordpress.com/about/)列出快速設置、易學、衝突而不敵對、流暢節奏、合理時長與重玩價值。 | 讓等待階段有清楚進度，但不以強制倒數催促朋友；動效不可增加回合空窗。檢查 3 人和 8 人送禮的差距，以及撲克／雷霆的長局是否讓未輪到者失去參與感。 |
| **3. 資訊與美術設計師**；參考 Daniel Solis | [卡片設計三原則](https://danielsolisblog.blogspot.com/2024/02/three-principles-of-card-design.html)：重要資訊應可見、排出主次，常見概念用簡短文字或圖示呈現。 | 禮物圖、牌面、玩家名稱、輪到誰與確認按鈕先建立一致層級；材質與插畫再進場。圖示仍需名稱、可聚焦提示與可讀替代文字；不讓華麗畫框擠掉手機上的關鍵數值。 |
| **4. 新手 UX 評審**；參考 Celia Hodent | 她的[新手引導文章](https://celiahodent.com/gamers-brain-ux-onboarding/)討論注意力、工作記憶與在操作中理解目標；[投入與沉浸文章](https://celiahodent.com/gamers-brain-part-3-ux-engagement-immersion-retention-gdc17-talk/)將可理解的回饋、自主感與能力感連到體驗。 | 首局讓玩家能說出「目標是什麼、現在輪到誰、下一步可做什麼、操作是否成功」。教學、彈幕與成就不要同時爭奪注意；先找新玩家實測，再說體驗變好。其即時動作遊戲案例不能直接照搬至回合制桌遊。 |
| **5. 動效與音效評審**；參考 Jan Willem Nijman | 作者在[個人網站](https://www.jwaaaap.com/)列出自己的教學演講[《The Art of Screenshake》](https://www.youtube.com/watch?v=AJdEqssNZ-U)，展示動畫、命中反應、聲音與鏡頭回饋如何讓基本操作更有手感。 | 只在伺服器確認後，以短暫且局部的演出標示下注、碰撞、翻牌、揭曉、送禮與入房；遊戲中的新演出應可靜音、跳過並保留文字結果。反對照搬射擊遊戲的全頁震動、連續閃光或為演出延遲下一回合。影片來源可由作者網站確認；本文不聲稱逐字轉錄演講。 |

## 每次討論怎麼用

給九個 AI 評審相同的功能描述、目前程式行為、玩家回饋與限制。每位先用自己的來源理念提出**一項可測的改進、一項反對條件、一項需觀察的證據**；第二輪交叉評論，不把角色的來源人物說成真的參與。由主持者整合成「可立即做／需原型測試／暫緩」，明列分歧和取捨。公開來源只支持理念；尺寸、秒數、門檻、排序和實作方式都應標為本專案假設。

| 範圍 | 九視角提出的下一個小改良（本專案推論） | 先檢查什麼，避免做錯 |
| --- | --- | --- |
| **德州撲克** | 情緒、節奏與資訊視角主張在現有行動區更清楚標示本次跟注額、行動後籌碼與輪到誰；已公開的攤牌結果可用短暫局部強調。 | 不在未輪到時執行預選動作，不提前顯示他人手牌；先請新玩家說明自己看懂了哪些數字。 |
| **雷霆之路** | 動效、美術與新手視角希望碰撞結果指出命中車、格位、損傷原因；輪到自己時讓行動車與合法目的地容易找。 | 只標已確定資訊，不預示骰子或隱藏事件；背景效果不能蓋住賽道和車位。 |
| **同頻俱樂部** | 社交與新手視角希望全員作答後，結果頁先讓人看見答案如何聚成多數，再清楚說明得分。 | 不在揭曉前透露秘密答案；完整結果應即刻可讀，不因逐步演出而等待。 |
| **送禮達人** | 情緒與社交視角想讓玩家看出「哪份禮物符合了朋友哪個喜好」，並保留短暫拆禮焦點。 | 現有完整結果和本機略過必須保留；8 人一輪可有 56 筆送禮，不強制逐件播完，也不讓一人「全桌略過」控制其他玩家。 |
| **大廳** | 視覺與節奏視角想讓可加入房間、玩家人數與操作入口比裝飾醒目；平滑移動維持朋友同場的感受。 | 公開站在另一台電腦的實際行走感與進房操作仍待玩家確認；房間「預估時長」沒有可信資料前不顯示。 |
| **成就** | 五枚入門徽章後，可研究「四桌巡禮」或一局中的共同趣事，但不增加勝率榜、能力獎勵或刷投稿數徽章。 | 由伺服器依正式結算授予、去重；先觀察是否誘使速刷、亂跟注或故意撞車，私人喜好及未公開牌不得進入分享。 |

### 交叉評審後的取捨

1. **公開「本局趣事卡」暫緩。** 社交視角起初想讓玩家在結算後選一幕、寫一句話公開到大廳。資安視角指出這會新建公開內容與他人資料的權限邊界：至少要驗證參與紀錄、預覽後主動發布、預設隱去他人姓名與房間碼、限制文字並可刪除。節奏視角支持小原型；社交視角在交叉評論後改主張先用四款既有結算頁各一行**可忽略的聊天引子**，例如「哪手最意外？」或「哪份禮物最懂你？」。先觀察玩家是否自發聊天、是否續桌；不儲存回答、不加倒數。這是低資源的研究候選，尚未實作。
2. **揭曉保留每人自主。** 動效視角想增加共同節拍；懷疑派玩家擔心蓋過朋友當下的反應。維持「完整結果先可讀、少量焦點可看可略過」；同頻的答案分布與雷霆碰撞原因先做靜態資訊草圖，若試玩仍看不懂，再加短動畫。送禮的本機略過不改為全桌控制。
3. **大廳減少動態有明確分歧。** 動畫工程與無障礙視角認為在 `prefers-reduced-motion: reduce` 下仍播放大廳行走，與[系統偏好的原意](https://www.w3.org/TR/mediaqueries-5/#prefers-reduced-motion)有衝突；玩家已明確要求**不新增開關，預設不減少這段動畫**，而且公開站因此才修正了「瞬移」。目前依玩家決定維持平滑位移；其他遊戲的減少動態處理不改。此例外及其可近用性代價保留在紀錄中，未來以真實使用者回饋重新評估，不把一般動效原則冒充成目前產品行為。[部署與背景驗證](LOBBY-MOVEMENT-PROGRESS.md)。
4. **成就先證明不扭曲玩法。** 情緒與社交視角重視共同回憶；桌遊節奏與懷疑派反對刷局；工程與資安視角要求事件判定、去重、只展示本人。保留[現有五枚入門成就](IMMERSIVE-EXPERIENCE-RESEARCH.md#第一版候選五枚容易理解的徽章)；「四桌巡禮」等候真人局觀察，解鎖通知只在本人結算後顯示文字，重連不重播。

### 執行順序與資源

| 順序 | 可交付的最小範圍 | 現有資源／驗收 |
| --- | --- | --- |
| **先驗證** | 由好友各玩一局，記錄是否能說出「輪到誰、能做什麼、剛剛發生什麼」，並確認另一台電腦上的大廳行走感。 | 用既有網站與遊戲結果頁；記錄誤解和等待時間，不需要新素材。 |
| **第一個低資源原型** | 四款遊戲各做一版結算頁聊天引子與資訊主次草圖；僅用文字和現有 CSS，不改規則或資料庫。 | 既有角色、禮物圖、牌桌與賽道即可；比較加入前後，玩家是否更容易解釋結果、是否會自然討論。 |
| **試玩後再決定** | 為最不易讀懂的單一結果事件做一段可略過的局部演出；五枚徽章以外的成就先寫可判定條件和負面誘因。 | 既有送禮焦點、Kenney 音效與 CSS 可借鑑；不因免費素材可下載就直接複製未核授權的動畫。 |
| **暫緩** | 公開趣事卡、全桌強制倒數／跳過、勝率榜、獎勵能力、整頁震動、需新插畫或未核授權音樂的方案。 | 這些需要新隱私設計、規則驗證或額外美術資源；目前沒有這些前置成果。 |

若進入實作，先把每項提案寫成「原作設計 → 套用範圍 → 不採用部分 → 素材授權 → 驗收方式」，再記入對應遊戲的進度文件。公開文章或影片可供研究，**不等於**其圖片、聲音與角色可直接部署；已核對的免費素材見[素材來源備忘](GAME-ASSET-SOURCES.md)。
