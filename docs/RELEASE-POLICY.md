# 版號與打版規範

## 版號來源與顯示

`package.json.version` 是唯一程式版號來源。`GET /api/version` 回 `{ "version": "1.1.0" }`，不含帳戶、主機資訊、Git路徑或秘密，且禁止快取。所有遊戲共用右上角設定的版本列；第一次展開時讀一次，成功後該頁不重複請求、不輪詢。網路失敗顯示提示，下次展開重試。

目前只採正式 `X.Y.Z` 格式，不使用先行版或build suffix。版本管理導入前的package基線為1.0.0，第一個實際標記版為1.1.0；不把舊提交事後冒稱已打版。程式版號、Git commit與SQLite schema是不同資訊，升版不會自行升降DB schema。

## 何時升版

依 [SemVer 2.0.0](https://semver.org/lang/zh-TW/) 採以下規則。本站相容性包含HTTP／移轉工具契約、玩家已儲存的設定、題目ID與資料讀取方式。

| 變更 | 升版 | 例子 |
| --- | --- | --- |
| 新功能、玩法、可見功能擴充或題庫分類擴充 | minor：1.1.2→1.2.0 | 新遊戲、共看、新工具、meme分類；即使先不PR，也必須打版 |
| 相容修正、效能／排版／安全修補 | patch：1.1.2→1.1.3 | 遮擋、同步錯誤、錯誤提示與既有題目勘誤 |
| 不相容API、移轉格式、移除契約或無法讀取既有資料 | major：1.1.2→2.0.0 | 同時提供遷移／回退說明；不能僅因DB新增相容表就判major |
| 純文件、測試或維持相同行為的開發整理 | 不升 | 更新驗收證據，不改已發版本tag |

同一批尚未發布的功能合併成一次版號，取最高影響；不必每個commit升一次。發布後的程式內容不可用相同版號替換，也不可移動／重建既有tag。不同分支準備同一版號時，整合後重新確認基準與發布範圍，避免兩份不同程式共用版號。

## 操作流程

1. 核對目前／上一正式版及變更範圍，決定minor／patch／major。不要靠程式自動猜測產品相容性。
2. 使用升版指令，例如：

   ```powershell
   npm run release:bump -- minor --summary "新增版本資訊與打版工具" --date 2026-10-06
   ```

   指令同步更新package、CHANGELOG，若有package-lock也同步；省略日期時採UTC當日。摘要是單行、最多240字。逐檔使用rename避免半份JSON；整批不是檔案系統交易，中斷後用Git diff及check修復，不可帶著不一致發布。
3. 補充CHANGELOG玩家看得懂的功能／修正、遷移或限制，執行：

   ```powershell
   npm run release:check
   npm run release:check -- --base <上一正式版tag或commit> --type minor
   npm test
   ```

   `check`驗證版號、日期、最新CHANGELOG摘要與排序／唯一性及lock同步；帶base才會核對升版幅度。新增功能的驗收必須指定`--type minor`，不相容則major；未升版或幅度不足回非零。`npm test`前自動執行不帶base的基本檢查，無Git目錄的發布包也可測試。
4. 測試通過後，提交本批程式、版號及紀錄；在乾淨提交建立annotated tag：`git tag -a v1.1.0 -m "Release v1.1.0"`。tag指向受測試的程式提交；後续純驗收文件可另提交，不移動tag。工具不自動commit、tag、push、合併或部署。
5. 依現有授權發PR／發布；部署封存tag或其固定commit，排除本機私人文件。使用隔離候選測試、資料備份／必要的migration預演及健康檢查；有DB變更時不能只回退程式tag。
6. 正式切換後驗`/api/version`、設定版號、受影響資源及既有帳戶，部署文件記錄版號、固定commit、測試數、備份、資料檢查與限制。未完成公開驗收只能標候選或待驗。

工具不分析程式差異來判定「新功能」，也不自動檢查tag已發布到遠端；這些由實作者與reviewer依變更範圍判斷。檢查通過不代表允許清除房間、覆寫正式帳戶或轉移其他站資料。
