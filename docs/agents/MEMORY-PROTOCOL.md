# 記憶更新與角色攻防協議

## 開始工作

讀索引、共用偏好、自己的角色檔與當前 spec。確認工作目錄／Git 分支、最新程式與部署來源；舊交接中的授權、房碼、測試結果不能替代目前狀態。只載入本次需要的來源，疑問先用程式、目前畫面與官方文件核對。

## 記錄規格

| 欄位 | 要求 |
| --- | --- |
| 日期／範圍 | 實際查核日、角色、遊戲、版本或研究階段。 |
| 結論類型 | 使用者偏好／程式事實／實玩觀察／外部來源／設計推論／待驗證。 |
| 證據 | 程式路徑、具體網頁連結、重現步驟、視窗尺寸、角色與結果；不要只寫「已測」。 |
| 結論與限制 | 哪個場景成立，哪些情況未驗證；評分為 NA 的項目不得算成零。 |
| 後續行動 | 具體 owner、可驗收条件、與其他角色的依賴。 |
| 替代舊記憶 | 指出取代哪一節；歷史留日期，不把過時提案當現況。 |

使用者偏好持續有效直到新指令改變；程式事實在相關程式更動時重讀。API／授權／外部政策在採用與實作前重新上網查核，不因一次研究就永久有效。評論是個人取向，保留作者語境與樣本偏差；引用摘要，不複製整篇。短角色檔保存穩定的方法及決策，詳細來源留研究文件，避免無限堆疊。

## 討論流程

設計方提出候選、預期樂趣與可判定事件；玩家方用 rubric 找反例、指出受影響玩家；程式方核對伺服器是否能可靠判定、去重及恢復。依實際訊息記錄提案 → 質疑 → 修訂 → 狀態，沒有回覆不能寫成同意。未收斂項目列待驗證，決策不以 agent 數量投票。

無厘頭成就可來自自然巧合或失敗後的幽默；不得因徽章鼓勵故意拖延、斷線、侮辱同桌、灌投稿或公開秘密。勝利紀錄與趣味徽章分開；伺服器、持久 identity、正常結算與冪等規則由程式／資料方確認。

## 完成工作

更新角色記憶的本輪新知、spec 狀態與進度；對照實作是否真的存在。主 agent 查來源可訪問、文件內連結、關鍵 schema／API 與現有程式是否一致，私有資料未進 Git。將可重現缺口與尚未完成的驗收留給下一輪；不僅留下「完成」兩字。
